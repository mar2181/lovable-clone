### P0 — BUILD ENGINE DOWN (SSE silent hang) [REGRESSED — was RESTORED June 7]

**This is the core product. It is broken.**

Two independent tests (180s + 120s timeouts) confirm: the build SSE stream opens and sends initial events, then **stalls permanently** — no `build_complete`, no `error` event, just silence until timeout.

Observed SSE event sequence (identical on both attempts):
```
{"type":"build_start","totalPages":4,"totalBatches":2}
{"type":"batch_start","batchIndex":0,"totalBatches":2,"pages":["Home","About Us","Services"]}
{"type":"page_status","page":"Home","status":"generating"}
{"type":"page_status","page":"About Us","status":"generating"}
{"type":"page_status","page":"Services","status":"generating"}
[silent for remaining ~175s → timeout]
```

This is **NOT** an "Insufficient credits" rejection (those return an `error` event immediately). The hang is inside the LLM API call for page generation — the worker sends a request to the upstream AI provider and never receives a response within the Cloudflare Worker CPU/wall-clock limit. The worker has no per-page timeout guard, so it goes silent rather than emitting an error.

**Pattern:** Audit PRs show this has been P0 since at least July 7 (4+ weeks of consecutive RED reports: PR #39, #42, #45, #49, #51, #53, #56).

**Fix (needs local/vault access):**
1. Check Cloudflare Worker tail logs for the `/api/build` route — look for upstream fetch timeout or 429/503 from the LLM provider.
2. Verify the OpenRouter/LLM API key in Worker secrets is valid and has quota: `wrangler secret list` → confirm `OPENROUTER_API_KEY` is set; check OpenRouter dashboard for balance/quota.
3. If credits exhausted: top up OpenRouter credits (was the fix in June 7 baseline).
4. If credits OK but still hanging: add a `Promise.race(fetch(...), timeout(60000))` guard around each page's LLM call in the build route, emitting `{"type":"error"}` on timeout rather than going silent.

### P0 — /dashboard RETURNS 404 [PERSISTS — first seen June 19, ~11 weeks]

**Root cause NOW CONFIRMED:** The deprecated `middleware.ts` convention in Next.js 16.x is causing Clerk's `auth.protect()` to perform a **`protect-rewrite`** to `/404` rather than a `302` redirect to `/sign-in`. This is a breaking change in Next.js 16 that the last audit flagged as `P3 hygiene` — it has silently become a P0 production outage.

Response headers from prod `GET /dashboard` confirm it:
```
x-matched-path: /404
x-clerk-auth-reason: protect-rewrite, session-token-and-uat-missing
x-clerk-auth-status: signed-out
x-vercel-cache: HIT
age: 983145    ← CDN-cached for ~11.4 days since ~2026-07-24
```

The dashboard route (`app/dashboard/page.tsx`) **exists in the repo** and is correctly compiled by `next build` (`○ /dashboard` — static). The local build passes cleanly (0 TypeScript errors). The failure is entirely a prod-deployment/middleware bug.

**Fix (repo change → flag):**
1. **Rename `middleware.ts` → follow the Next.js 16 `proxy` convention:**  
   Read https://nextjs.org/docs/messages/middleware-to-proxy for the exact rename/migration steps.  
   The file is at `/home/user/lovable-clone/middleware.ts`.
2. **Verify `NEXT_PUBLIC_CLERK_SIGN_IN_URL`** (or `signInUrl` in Clerk config) is explicitly set so `auth.protect()` has a valid redirect target after migration.
3. **Deploy to Vercel** (triggers new build).
4. **Purge Vercel CDN cache** for `/dashboard` via Vercel dashboard or `vercel cache purge /dashboard` — the 404 response has been hard-cached since July 24 and will keep serving even after the fix deploys until purged.
