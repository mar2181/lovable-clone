### P0 — Dashboard returns 404 for unauthenticated users [PERSISTS — ~50 days unfixed]

**Symptom:** `GET https://hswebappbuilder.space/dashboard` → HTTP 404 (Next.js `_not-found` page). `/` returns 200; `/sign-in` returns 200. Dashboard is completely inaccessible to users who aren't already logged in.

**History:** First flagged in audit PRs from ~2026-06-08. Every audit PR from #27 (June 19) through #51 (July 25) reports this. **This run confirms it persists.**

**Root cause:** `middleware.ts` calls Clerk's `auth.protect()` for non-public routes. In Clerk 7.5.20, when `NEXT_PUBLIC_CLERK_SIGN_IN_URL` is not set in the Vercel environment, `auth.protect()` calls Next.js `notFound()` instead of redirecting to `/sign-in`. Local build shows `/dashboard` as a valid static route — bug is Vercel-deployment-specific. No middleware code changes since June 7; this is a Vercel env var issue.

**Fix (Vercel env var — no code change needed):**
1. Log into Vercel → Project Settings → Environment Variables (Production)
2. Add: `NEXT_PUBLIC_CLERK_SIGN_IN_URL` = `/sign-in`
3. Trigger a redeploy (or the variable takes effect on next deploy)
4. Verify: `curl -IL https://hswebappbuilder.space/dashboard` should now show a 307/308 redirect to `/sign-in`, not a 404.

**Alternative fix (code, more robust):** Replace `auth.protect()` in `middleware.ts` with an explicit redirect:
```ts
const clerkAuthMiddleware = clerkMiddleware(async (auth, request) => {
  if (!isPublicRoute(request)) {
    const { userId } = await auth()
    if (!userId) {
      return NextResponse.redirect(new URL('/sign-in', request.url))
    }
  }
})
```
This works regardless of `NEXT_PUBLIC_CLERK_SIGN_IN_URL` being set.

**History:** Down since approximately June 22 (first flagged in PR #29). Audit PR #51 (July 25) title says "voice box **terminated**" — the RunPod pod may have been deleted, not just stopped. `RUNPOD_API_KEY` is absent in cloud so pod state cannot be confirmed here.

**Wiring integrity:** `pet-concierge.tsx` and `next.config.ts` are INTACT — `data-backend=selfhosted`, `/boxapi` proxy, and pod URL all correct in the repo. The issue is the pod runtime, not the wiring.

**Critical question: is the pod stopped or deleted?**  
A stopped pod returns 404 from its proxy URL and can be restarted. A deleted/terminated pod's URL is permanently invalid — the Pod ID `udcz4k7kse1zw6` is gone and a new pod would get a different ID, requiring a `next.config.ts` update + redeploy.

**Fix (local — must check RunPod dashboard first):**
```bash
# 1. Check pod state:
curl -H "Authorization: Bearer $RUNPOD_API_KEY" \
  https://rest.runpod.io/v1/pods/udcz4k7kse1zw6
# If pod exists and is STOPPED/EXITED:
curl -X POST https://rest.runpod.io/v1/pods/udcz4k7kse1zw6/start \
  -H "Authorization: Bearer $RUNPOD_API_KEY"
# If pod is DELETED: provision a new pod, update next.config.ts /boxapi destination to new URL.
```

### P2 — Build engine: 4-page builds exceed 180s timeout [CONFIRMED — PERSISTS]

SSE pipeline is healthy (HTTP 200, stream opens, files generated, no credit or OpenRouter errors). But a 4-page build takes 175–240s end-to-end due to sequential LLM generation per batch, reliably missing the 180s default timeout.

**Run 1 (175s):** `build_start` (4 pages, 2 batches) → Batch 0 complete (7 files: App.tsx, Header, Footer, Home, About, Services, constants) → Batch 1 (`Contact`) stalled at `page_status:generating` → stream cut at 175s. No error events.
**Run 2 (240s):** Stream stalled at LLM generation phase for all 240s (OpenRouter latency spike).

The infrastructure and auth are healthy. The bottleneck is OpenRouter LLM response latency under load.

**Fix:**
- Increase SSE client timeout to 300s (or add a server-side keepalive ping every 30s)
- A single-page description likely completes in 60–90s — use that for the audit probe to get a definitive GREEN/RED
- `wrangler.toml`: consider increasing `compatibility_flags` or Cloudflare's 100s CPU limit for long-running SSE routes (CPU vs wall-clock distinction)
