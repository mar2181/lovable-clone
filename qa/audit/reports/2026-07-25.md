**5th consecutive audit with build engine broken.** The SSE stream starts, Batch 0 completes successfully (~52s, 3 pages, 23 files emitted in `batch_done`), then the engine requests Batch 1 (Contact page) and goes completely silent. No error events, no `build_complete`. The 180-second curl timeout is the only circuit breaker, which fires every time.

```

POST /api/build/PHyBD5SXoB → SSE open
  0s:  build_start, batch_start (batch 0), page_status×3 generating
  ~39s: batch_stream — all batch 0 files
  ~51s: page_status done ×3; batch_done with 23 files

  52–180s: *** COMPLETE SILENCE ***
  180s: curl timeout kills stream

DELETE /api/projects/PHyBD5SXoB → 200 {"success":true}
```

**Root cause (suspected):** Second LLM call to OpenRouter hangs — no error returned (not an "Insufficient credits" case, which was the June cause). Likely an OpenRouter cold-start stall or a backend timeout that doesn't surface as an error event. The batching logic schedules a second batch for any build with 4+ pages; any 4-page prompt will hang on the second call.

**Fix — needs investigation:**
1. Check OpenRouter dashboard for hung or error'd calls around the above timestamps.
2. Add a per-batch timeout in `worker/src/build.ts` (or wherever batch orchestration lives) — if a batch LLM call takes >90s, emit `{"type":"error","message":"batch timeout"}` and close the stream.
3. Consider adding a server-side SSE keepalive ping every 15s so clients can distinguish a live-but-slow stream from a dead one.
4. Root-cause why the second batch call hangs but doesn't error — may be an OpenRouter streaming timeout that the worker doesn't handle.

### P0 — Voice box pod terminated (~19 days down)

The RunPod pod `udcz4k7kse1zw6` returned HTTP 404 on both `GET /healthz` and `GET /` (root). A 404 from the RunPod proxy layer (not app-level) is the signature of a **terminated or expired pod** — a crashed pod returns 502/503; 404 means the proxy endpoint itself no longer resolves to a live container. Per-policy this is auto-fixable via pod restart, but the 19-day duration suggests the pod was terminated (billing/expiry), not merely crashed.

**Live evidence:**
```
GET https://udcz4k7kse1zw6-7860.proxy.runpod.net/healthz → HTTP 404
GET https://udcz4k7kse1zw6-7860.proxy.runpod.net/         → HTTP 404
```

**Impact:** All pet-concierge voice sessions fail for all users. The `pet-concierge.tsx` wiring is correct (`data-backend="selfhosted"`, `/boxapi`), and `next.config.ts` correctly proxies `/boxapi → https://udcz4k7kse1zw6-7860.proxy.runpod.net`. But no live pod answers.

**Two-step fix:**
1. **Provision a new RunPod pod** (RunPod console) and obtain its new proxy URL (new pod ID + port).
2. **Update `next.config.ts`** — one line: change `https://udcz4k7kse1zw6-7860.proxy.runpod.net` to the new URL, then `git push` + `vercel deploy`. The frontend agent confirmed this is the only place the URL lives.

**Cannot auto-fix in cloud:** requires `RUNPOD_API_KEY` (pod provisioning) and a repo push (URL update). Both are flagged for Mario.

**Secondary concern:** No auto-fallback in `pet-concierge.tsx`. When box is down, voice fails hard with no circuit-breaker or fallback to ElevenLabs. Emergency rollback: delete two lines in `pet-concierge.tsx` (marked "INSTANT ROLLBACK") and redeploy.

### P1 — `middleware.ts` uses deprecated Next.js convention

Next.js 16.2.6 (current install) prints a deprecation warning at build time:

```
The "middleware" file convention is deprecated. Please use "proxy" instead.
```

The Clerk auth guard, public-route matcher, and `DEV_BYPASS` logic all live in `middleware.ts`. On a future Next.js upgrade, the file will be **silently ignored**, disabling all authentication on the frontend.

**Fix:** Rename `middleware.ts` → `proxy.ts` (verify the export signature hasn't changed in Next.js docs, as the API may differ). Low risk, high urgency.

### P2 — `/dashboard` returns 404 to unauthenticated users (6+ weeks)

The `/dashboard` route exists, compiles, and serves correctly for logged-in users. However, unauthenticated requests get an HTTP 404 (`x-matched-path: /404`, `x-clerk-auth-reason: protect-rewrite`) instead of a redirect to `/sign-in`.

**Expected behavior:** `auth.protect()` in `middleware.ts` should issue a 302 to `/sign-in`. Instead, Clerk is rewriting to `/404`. This suggests `NEXT_PUBLIC_CLERK_SIGN_IN_URL` (or equivalent) is not set in the Vercel production environment, causing Clerk to not know where to redirect and falling back to 404.

**Impact:** Any logged-out user who navigates directly to `/dashboard` gets a dead-end 404 page with no call to action. This has been the behavior since approximately June 8 (confirmed via 7+ consecutive audit reports).

**Fix:** Set `NEXT_PUBLIC_CLERK_SIGN_IN_URL=/sign-in` in Vercel project environment variables and redeploy. Verify with: `curl -si https://hswebappbuilder.space/dashboard | grep location` — should see a 302 to `/sign-in`.
