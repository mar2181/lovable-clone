### P0 — BUILD ENGINE DOWN (SSE silent hang) [PERSISTS — 31+ days, 9 consecutive RED reports]

**This is the core product. It is broken.**

Both the probe and the deep E2E confirm: the build SSE stream opens, sends 5 initial events, then **stalls permanently** — no `build_complete`, no `error` event, just silence until curl timeout at 180s.

Observed SSE sequence (identical on every attempt since July 7):
```
{"type":"build_start","totalPages":4,"totalBatches":2}
{"type":"batch_start","batchIndex":0,"totalBatches":2,"pages":["Home","About Us","Services"]}
{"type":"page_status","page":"Home","status":"generating"}
{"type":"page_status","page":"About Us","status":"generating"}
{"type":"page_status","page":"Services","status":"generating"}
[silent for ~175s → timeout]
```

This is **NOT** an "Insufficient credits" rejection (those return `{"type":"error"}` immediately). The hang is inside the LLM API call — the worker sends a page-gen request to the upstream AI provider and never receives a response within the Cloudflare Worker wall-clock limit. Because there is no per-page timeout guard, the worker goes silent rather than emitting an error.

**Consecutive RED:** PRs #39, #42, #45, #49, #51, #53, #56, #58, and now this run (#11). No fix has landed.

**Fix (needs local/vault access):**
1. `cd worker && wrangler tail --format=pretty` — filter `/api/build` route; look for upstream fetch timeouts or 429/503 from OpenRouter.
2. Check OpenRouter dashboard: verify the API key has balance. If credits exhausted → top up (this was the fix in the June 7 baseline that RESTORED the engine then).
3. If balance OK but hang persists: add a `Promise.race([fetch(…), timeout(60_000)])` guard around each page LLM call, emitting `{"type":"error","message":"page timeout"}` on expiry rather than going silent.

### P0 — /dashboard RETURNS 404 [PERSISTS — ~79 days since June 19]

`curl -I https://hswebappbuilder.space/dashboard` this run:
```
HTTP/2 404
x-matched-path: /404
x-clerk-auth-reason: protect-rewrite, session-token-and-uat-missing
x-clerk-auth-status: signed-out
x-vercel-cache: HIT
age: 14
```

**Root cause (confirmed in 2026-08-04 report):** The deprecated `middleware.ts` convention in Next.js 16.x causes Clerk's `auth.protect()` to perform a `protect-rewrite` to `/404` instead of a `302` redirect to `/sign-in`. Users who try to access the dashboard see a 404 page rather than being prompted to log in. The dashboard route (`app/dashboard/page.tsx`) **exists and compiles correctly** (confirmed: `○ /dashboard` in `next build` output, 0 TypeScript errors). This is a prod deployment bug only.

**Status:** Vercel CDN is still actively caching the 404 (HIT, age=14s). The cache is still live from the stale deployment.

**Fix (repo change → flag — full steps in PR #58 body):**
1. Rename `middleware.ts` → follow the Next.js 16 `proxy` convention. See: https://nextjs.org/docs/messages/middleware-to-proxy
2. Verify `NEXT_PUBLIC_CLERK_SIGN_IN_URL` is set in Vercel env vars so `auth.protect()` knows where to redirect.
3. Deploy to Vercel (triggers new build).
4. Purge Vercel CDN cache for `/dashboard` via `vercel cache purge /dashboard` or the Vercel dashboard.
